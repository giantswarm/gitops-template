This page lists the directories and files of the repository and the rules for them. For how Flux turns them into
clusters, see [How it works](../how-it-works.md).

## Layout

The repository follows the hierarchy of the platform: a management cluster has organizations, and an organization
has workload clusters.

```text
.sops.yaml
bases
├── apps
├── clusters                                            cluster bases, see guides/clusters.md
|   ├── PROVIDER                                        a provider's base, such as capa
|   └── [BASE_NAME]                                     a cluster base built on a provider's base
├── environments
├── secret_stores
├── shared_objects
└── stacks                                              several apps deployed together, see guides/stacks.md
management-clusters
└── MC_NAME
    ├── .sops.keys
    ├── [kustomization.yaml]
    ├── [OTHER_RESOURCES]
    ├── secrets
    |   └── MC_NAME.gpgkey.enc.yaml
    ├── MC_NAME.yaml
    └── [organizations]
        ├── [kustomization.yaml]
        └── ORG_NAME
            ├── kustomization.yaml                      sets the organisation's name, see below
            ├── [OTHER_RESOURCES]                       in `default`
            ├── ORG_NAME.yaml
            ├── namespace.yaml                          applies namespace/ into the organisation's namespace
            ├── namespace                               namespace.yaml responsibility, never MC_NAME.yaml's
            |   ├── kustomization.yaml
            |   ├── [OTHER_RESOURCES]                   in the organisation's namespace
            |   ├── [secrets]                           kept by Flux, as MC_NAME's secrets are
            |   |   ├── kustomization.yaml
            |   |   ├── [WC_NAME.gpgkey.enc.yaml]       a workload cluster's SOPS key
            |   |   └── [WC_NAME-direct.gpgkey.enc.yaml]
            |   ├── [notifications]                     the organisation's commit statuses
            |   ├── [shared-objects]                    objects every organisation shares, see add_mc.md
            |   ├── [workload-cluster-secret-stores]    a SecretStore for every workload cluster, generated by Kyverno
            |   └── [workload-clusters]                 the workload clusters' Flux Kustomizations
            |       ├── kustomization.yaml
            |       ├── WC_NAME.yaml
            |       ├── [WC_NAME-apps.yaml]
            |       └── [WC_NAME-direct.yaml]
            ├── [multicluster]                          apps on several clusters, see guides/scheduled-updates.md
            |   ├── kustomization.yaml
            |   ├── apps.yaml
            |   └── apps                                apps.yaml responsibility
            |       ├── kustomization.yaml
            |       ├── clusters.yaml
            |       └── APP_NAME
            └── [workload-clusters]
                └── WC_NAME                             managed from namespace/workload-clusters
-----------------------------------------------------------------------------------
                    ├── kustomization.yaml                WC_NAME.yaml responsibility
                    ├── apps
                    ├── cluster
                    ├── [out-of-band]
                    |   ├── [kustomization.yaml]
                    |   └── [OTHER_RESOURCES]
                    └── [teams]                           application teams' repositories, see guides/app-teams.md
```

How to read it:

- Names in capital letters are placeholders. Replace them with your own names, following the [naming](#naming) rules.
  Lowercase parts stay as they are: `WC_NAME-apps.yaml` for a cluster `demo0` is `demo0-apps.yaml`.
- Names with an extension, like `MC_NAME.yaml`, are files. The rest are directories.
- Names in square brackets are optional. See [optional components](#optional-components).
- The horizontal line splits the work between the [Flux Kustomizations](#flux-kustomizations). `MC_NAME.yaml`
  applies everything above it but the organisation's `namespace`, which `namespace.yaml` applies, and the cluster's
  Kustomizations, in `namespace/workload-clusters`, apply the cluster directory below it, except `out-of-band`.
- `.sops.yaml`, `.sops.keys` and the `*.gpgkey.enc.yaml` files are only needed when you encrypt secrets with SOPS.
  See [SOPS keys](./sops-keys.md).

## Structure version

The structure on this page has a version, so a repository built on it can tell when it has fallen behind. The
current structure version is `3`. It goes up when an existing repository has to change to follow the structure, for
example when a directory moves or a naming rule changes. New examples and changes to the apps under `bases/` don't
change it.

`kubectl gs gitops` records the version in a `.gitops-metadata.yaml` file at the root of the repository, with an
entry for every management cluster, organization, workload cluster, app and base it created:

```yaml
apiVersion: gitops.giantswarm.io/v1alpha1
kind: RepositoryMetadata
structureVersion: 3
layers:
  - kind: management-cluster
    path: management-clusters/MC_NAME
    structureVersion: 3
```

The file sits outside of what Flux applies, so it never reaches a cluster. Don't edit it by hand.

To see which parts of your repository are behind, run this in your clone:

```sh
kubectl gs gitops check
```

It exits with an error when anything is behind, so you can run it in CI. If your repository is older than the
metadata file, run `kubectl gs gitops check --adopt` once to record what's there as current. It assumes what's there
is current, so it can't find drift from before you ran it.

To bring the repository up to date, first see which files would change:

```sh
kubectl gs gitops upgrade --dry-run
```

Then run the upgrade:

```sh
kubectl gs gitops upgrade
```

It changes the files in place and keeps your own edits where it can. Review the result with `git diff` before you
commit it. If something goes wrong, undo it with Git. That's why the command doesn't run on a repository with
uncommitted changes, or on a directory Git doesn't track, unless you pass `--force`. Migrations never touch files Git
ignores, such as decrypted secrets, so move those yourself.

Version 2 deploys clusters and apps with Flux `HelmRelease`s instead of App CRs. The upgrade to it doesn't convert
App CRs, because the `HelmRelease` has to take over the Helm release the App CR installed in the cluster. It fails on
every layer that still deploys or patches an App CR. Move those first, see the
[App Platform deprecation](https://docs.giantswarm.io/overview/fleet-management/app-management/app-platform-deprecation/).
Then it rewrites the user config patch of each workload cluster for the `HelmRelease`.

Version 3 drops the `mapi` directory of workload clusters. Its `cluster`, `apps` and any other directories move up
into the cluster's directory, next to `out-of-band`, and the cluster's `kustomization.yaml` lists what the cluster's
Kustomizations apply, never `out-of-band`, see [Flux Kustomizations](#flux-kustomizations). It also moves everything
an organisation keeps in its namespace into the organisation's `namespace` directory, which its own Kustomization,
`namespace.yaml`, applies, see [Move an organisation's namespace objects](#move-an-organisations-namespace-objects),
the workload clusters' Kustomizations and their SOPS keys among them, see
[Move the workload cluster Kustomizations](#move-the-workload-cluster-kustomizations).
kubectl-gs doesn't know version 3 yet: `kubectl gs gitops add workload-cluster` still generates `mapi`, the version 2
layout, and `kubectl gs gitops upgrade` has no migration to version 3. Move an existing cluster by hand, as the
[CHANGELOG](/CHANGELOG.md) describes.

Note that layers recorded without a structure version can't be upgraded. If you know the version they were created
with, set their `structureVersion` by hand. Otherwise, remove their entries and run
`kubectl gs gitops check --adopt`.

`check` and `upgrade` need kubectl-gs 6.0.0 or newer, see [kubectl-gs version](../appendices.md#kubectl-gs-version).
If yours is older, update it with `kubectl gs selfupdate`.

### Move an organisation's namespace objects

On a management cluster that already runs the repository, moving objects from what `MC_NAME.yaml` applies into the
organisation's `namespace` directory deletes them once. Flux deletes what leaves a `Kustomization`'s inventory in the
same reconciliation, and `MC_NAME.yaml` always applies a commit before the organisation's namespace `Kustomization`,
whose `dependsOn` names it, creates the objects again. Deleting the
`-direct` `Kustomization` deletes what it applied in the workload cluster, and deleting an `ExternalSecret` deletes the
Secret it wrote.

To move them without a deletion, use three commits, and let Flux apply each one before you push the next:

1. Annotate every object that moves with `kustomize.toolkit.fluxcd.io/prune: disabled`. `MC_NAME.yaml` applies the
   annotation, so Flux leaves the objects when they leave its inventory.
1. Move the objects into `namespace`, add `namespace.yaml`, and take them out of the organisation's
   `kustomization.yaml`, as in [Add an organization](../add_org.md). `MC_NAME.yaml` applies the commit first: it
   leaves the annotated objects where they are and creates `namespace.yaml`'s `Kustomization`, which then takes the
   objects over.
1. Remove the annotation, so Flux deletes the objects again when you delete them from Git. Leave it on SOPS key
   Secrets, such as a `-direct` `Kustomization`'s key in `namespace/secrets`: like the ones in `MC_NAME/secrets`,
   they keep `kustomize.toolkit.fluxcd.io/prune: disabled` for good, from `namespace/secrets/kustomization.yaml`.

A new management cluster needs none of this: its organisations' namespaces don't exist yet.

### Move the workload cluster Kustomizations

The workload clusters' Kustomizations, `WC_NAME.yaml`, `WC_NAME-apps.yaml` and the others, used to be in the
organisation's `workload-clusters` directory, in `default`, and the cluster keys in `MC_NAME/secrets`. On a management
cluster that already runs them, move them into the organisation's namespace in two commits, and let Flux apply the
first before you push the second. Before you start:

- The organisation's `namespace.yaml` runs, see [Move an organisation's namespace objects](#move-an-organisations-namespace-objects).
- kustomize-controller supports `spec.deletionPolicy`: `kubectl explain kustomization.spec.deletionPolicy` describes
  it. The Flux of Giant Swarm management clusters does.
- Move each cluster's Kustomizations together: the apps Kustomization names its cluster's in `dependsOn`, in its own
  namespace.

> **Warning:** don't move the files without the first commit. Flux deletes the old `Kustomization`s in `default` when
> their files leave `MC_NAME.yaml`'s build, and their finalizer deletes what they applied before the new ones in the
> organisation's namespace exist. Every app on the workload clusters would be uninstalled, and the clusters' values,
> `ExternalSecret`s and the Secrets they wrote, `PushSecret`s and application teams' `Kustomization`s would go. Only
> the clusters' `HelmRelease`s and `OCIRepository`s would stay. `deletionPolicy: Orphan` makes the finalizer delete
> nothing.

Export the names the commands below use:

```sh
export MC_NAME=CODENAME
export ORG_NAME=ORGANIZATION
export ORG_DIR=management-clusters/${MC_NAME}/organizations/${ORG_NAME}
```

1. The first commit moves nothing:

    - Add `deletionPolicy: Orphan` to every `Kustomization` in the organisation's `workload-clusters`. A `-direct` one
      there is a legacy cluster's, which stays in `default`, so leave it out:

      ```sh
      for f in ${ORG_DIR}/workload-clusters/*.yaml; do
        case "$(basename ${f})" in
          kustomization.yaml | *-direct.yaml) ;;
          *) yq -i '.spec.deletionPolicy = "Orphan"' ${f} ;;
        esac
      done
      ```

    - Add the rule for the workload clusters' keys in `namespace/secrets` to `.sops.yaml`, ahead of the other rules,
      so an organisation key's rule for `namespace/secrets` can't take them, see
      [SOPS keys](./sops-keys.md#encryption-rules):

      ```sh
      export MASTER_KEY_FP=$(gpg --show-keys --with-colons management-clusters/${MC_NAME}/.sops.keys/.sops.master.asc |
        awk -F: '/^fpr/{print $10; exit}')
      yq -i '.creation_rules = [{
        "encrypted_regex": "^(data|stringData)$",
        "path_regex": "management-clusters/'"${MC_NAME}"'/organizations/[^/]+/namespace/secrets/.*\\.(gpg|age)key\\.enc\\.yaml",
        "pgp": "'"${MASTER_KEY_FP}"'"
      }] + .creation_rules' .sops.yaml
      ```

    - Copy each key Secret those `Kustomization`s name in `decryption.secretRef` into the organisation's
      `namespace/secrets`, in the organisation's namespace, and list it in `namespace/secrets/kustomization.yaml`. If
      the organisation doesn't have that directory yet, create it as in [Add an organization](../add_org.md), with
      its `kustomization.yaml`, and list `secrets` in `namespace/kustomization.yaml`. With the master private key in
      your keyring, for each key file, such as `WC_NAME.gpgkey.enc.yaml`:

      ```sh
      export KEY_FILE=WC_NAME.gpgkey.enc.yaml
      sops --decrypt management-clusters/${MC_NAME}/secrets/${KEY_FILE} |
        yq '.metadata.namespace = "org-'"${ORG_NAME}"'"' > ${ORG_DIR}/namespace/secrets/${KEY_FILE}
      sops --encrypt --in-place ${ORG_DIR}/namespace/secrets/${KEY_FILE}
      yq -i '.resources += [strenv(KEY_FILE)]' ${ORG_DIR}/namespace/secrets/kustomization.yaml
      ```

   Push, and wait until `MC_NAME-gitops` and `MC_NAME-organization-ORG_NAME` are `Ready` at this revision. Check
   that every old `Kustomization` prints `Orphan`, and that the keys are in the organisation's namespace:

    ```sh
    kubectl get kustomization -n default -o custom-columns=NAME:.metadata.name,DELETION:.spec.deletionPolicy
    kubectl get secret -n org-${ORG_NAME} -l giantswarm.io/prevent-deletion=true
    ```

1. The second commit moves the `Kustomization`s:

    - Move their files into `namespace/workload-clusters`, list them in its `kustomization.yaml`, and list
      `workload-clusters` in `namespace/kustomization.yaml` if it isn't there yet. Delete
      `workload-clusters/kustomization.yaml`, and take `workload-clusters` and the replacement with
      `labelSelector: giantswarm.io/health-check-cluster=true` out of the organisation's `kustomization.yaml`.
    - Change each moved file as [Flux Kustomizations](#flux-kustomizations) describes: no `metadata.namespace` and no
      `giantswarm.io/health-check-cluster` label, `sourceRef.namespace: default`, `organization: "${organization}"`,
      `org-${organization}` as the namespace of a `Cluster` health check, the organisation's namespace
      `Kustomization` in `dependsOn` where there's no `dependsOn` yet, and no `deletionPolicy`:

      ```sh
      export ORG_KUSTOMIZATION=$(yq '.metadata.name' ${ORG_DIR}/namespace.yaml)
      mkdir -p ${ORG_DIR}/namespace/workload-clusters
      touch ${ORG_DIR}/namespace/workload-clusters/kustomization.yaml
      yq -i '.resources |= ((. // []) + ["workload-clusters"] | unique)' ${ORG_DIR}/namespace/kustomization.yaml
      yq -i 'del(.resources[] | select(. == "workload-clusters")) |
        del(.replacements[] | select(.targets[].select.labelSelector == "giantswarm.io/health-check-cluster=true"))' \
        ${ORG_DIR}/kustomization.yaml
      for f in ${ORG_DIR}/workload-clusters/*.yaml; do
        case "$(basename ${f})" in kustomization.yaml | *-direct.yaml) continue ;; esac
        git mv ${f} ${ORG_DIR}/namespace/workload-clusters/
        yq -i '.resources += ["'"$(basename ${f})"'"]' ${ORG_DIR}/namespace/workload-clusters/kustomization.yaml
        yq -i 'del(.metadata.namespace, .metadata.labels["giantswarm.io/health-check-cluster"], .spec.deletionPolicy) |
          del(.metadata.labels | select(length == 0)) |
          .spec.sourceRef.namespace = "default" | .spec.postBuild.substitute.organization = "${organization}" |
          with(.spec | select(has("healthChecks")) | .healthChecks[] | select(.kind == "Cluster");
            .namespace = "org-${organization}") |
          with(.spec | select(has("dependsOn") | not);
            .dependsOn = [{"name": strenv(ORG_KUSTOMIZATION), "namespace": "default"}])' \
          ${ORG_DIR}/namespace/workload-clusters/$(basename ${f})
      done
      git rm ${ORG_DIR}/workload-clusters/kustomization.yaml
      ```

      A legacy `-direct` `Kustomization` stays in `workload-clusters`: keep that `kustomization.yaml` instead, with only
      the `-direct` file in it, and keep `workload-clusters` in the organisation's `kustomization.yaml`.
    - Take the keys you copied out of `MC_NAME/secrets/kustomization.yaml`, and `git rm` their files there. Keep a key
      that a legacy `-direct` `Kustomization` in `default` still uses.

   Push. `MC_NAME.yaml` deletes the old `Kustomization`s, which leave what they applied, and leaves the old keys in
   `default`, as they have `kustomize.toolkit.fluxcd.io/prune: disabled`. `namespace.yaml` then creates the new
   `Kustomization`s, which decrypt with the keys the first commit put in the organisation's namespace and take over
   the objects without changing them: the `HelmRelease`s don't upgrade, and nothing is uninstalled. Check that the new
   ones are `Ready`, that none of the old ones is left, and that the objects name their new owner's namespace:

    ```sh
    flux get kustomizations -n org-${ORG_NAME}
    kubectl get kustomization -n default
    kubectl get helmrelease -n org-${ORG_NAME} -L kustomize.toolkit.fluxcd.io/namespace
    ```

1. Once nothing in `default` uses them, delete the old keys from `default` by hand. For each one, remove its label
   first:

    ```sh
    kubectl label secret -n default KEY_SECRET giantswarm.io/prevent-deletion-
    kubectl delete secret -n default KEY_SECRET
    ```

The cluster directories don't move, so the `path`s and the per-cluster rules in `.sops.yaml` stay as they are. The new
`Kustomization`s run as the organisation's `automation` ServiceAccount, which may write only in the organisation's
namespace: a cluster directory that applies anything else fails with "forbidden", see
[Flux Kustomizations](#flux-kustomizations).

## Naming

| Placeholder | Rule |
| --- | --- |
| `MC_NAME` | The management cluster's codename |
| `ORG_NAME` | The organization's name, in lowercase and without the `org-` prefix |
| `WC_NAME` | Any name, but the workload cluster's name is clearest |
| `PROVIDER` | The Cluster API provider, such as `capa`, as `kubectl gs gitops add base --provider` names it |
| `BASE_NAME` | Any name other than a provider's, such as `my-defaults` |

Files and resources use the names `kubectl gs gitops` generates, so it recognizes them in `gitops check`,
`gitops upgrade` and `gitops add automatic-update`:

| What | Name |
| --- | --- |
| Management cluster Flux `Kustomization` | `MC_NAME-gitops`, in `MC_NAME.yaml` |
| Workload cluster Flux `Kustomization` | `MC_NAME-clusters-WC_NAME`, in `WC_NAME.yaml`, in `namespace/workload-clusters` |
| Flux `Kustomization` of a workload cluster's secondary apps | `MC_NAME-clusters-WC_NAME-apps`, in `WC_NAME-apps.yaml`, in `namespace/workload-clusters`. `kubectl gs gitops` doesn't generate it, see [Flux Kustomizations](#flux-kustomizations) |
| An app's `HelmRelease` and `OCIRepository` when it's a base app, installed with the cluster | the same files, in `cluster/apps/APP_NAME` |
| Out-of-band Flux `Kustomization` | `MC_NAME-clusters-WC_NAME-direct`, in `WC_NAME-direct.yaml`, in `namespace/workload-clusters` |
| Flux `Kustomization` of an organisation's namespace | `MC_NAME-organization-ORG_NAME`, in `namespace.yaml`. `kubectl gs gitops` doesn't generate it |
| Flux `Kustomization` of an organisation's apps on several clusters | `MC_NAME-multicluster-apps-ORG_NAME`, in `multicluster/apps.yaml`. `kubectl gs gitops` doesn't generate it |
| An app's `HelmRelease` and `OCIRepository` | `helm-release.yaml` and `oci-repository.yaml`, one resource each, in `apps/APP_NAME` |
| A workload cluster's values | `cluster_userconfig.yaml` with the `${cluster_name}-cluster-userconfig` ConfigMap, in `cluster` |
| The patch that adds them to the cluster's `HelmRelease` | `patch_cluster_userconfig.yaml`, in `cluster` |
| A workload cluster's region | a `components:` entry for `bases/environments/regions/REGION`, in `cluster/kustomization.yaml`. Every cluster needs one, or it would be created in the management cluster's region and CI fails, see [Regions](../guides/environments.md#regions). `kubectl gs gitops` doesn't generate it |
| A workload cluster's stage | a `components:` entry for `bases/environments/stages/STAGE`, in `cluster/kustomization.yaml`, optional, see [Stages](../guides/environments.md#stages). `kubectl gs gitops` doesn't generate it |
| A provider's cluster base | `cluster.yaml`, `cluster_config.yaml` and `kustomization.yaml`, in `bases/clusters/PROVIDER` |
| A cluster base built on a provider's base | `kustomization.yaml` and its own files, in `bases/clusters/BASE_NAME`, next to the provider's base and never inside it, see [Cluster bases](../guides/clusters.md) |
| A stack, several apps deployed together | `kustomization.yaml` and a values file per app, in `bases/stacks/STACK_NAME`, see [Stacks](../guides/stacks.md). `kubectl gs gitops` doesn't generate it |

Repositories forked before the template used these names can move to them with
[Move a fork to the kubectl-gs file and resource names](../guides/kubectl-gs-names.md).

## Optional components

### `[OTHER_RESOURCES]`

These are any other Kubernetes resources you add, as files or directories, at the level they belong to. When you
have more than a few, group them by kind:

```text
management-clusters
└── demomc
    ├── secrets
    |   ├── secret-1.enc.yaml
    |   └── secret-2.enc.yaml
    └── configmaps
        └── cm.yaml
```

### `[kustomization.yaml]`

If a directory has no `kustomization.yaml`, Flux generates one that includes every file in it and in its
subdirectories, until it finds a `kustomization.yaml`. Add one when you want to list the resources yourself or use
other [kustomize features](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#kustomize-feature-list).

If you add one, include this option. It records in every resource the file it came from, which makes debugging
easier:

```yaml
buildMetadata: [originAnnotations]
```

### `[organizations]` and `[workload-clusters]`

These directories keep the organizations apart from the management cluster's other resources, and the workload
clusters apart from the organization's other resources. Use them when there are other resources at the same level:

```text
management-clusters
└── demomc
    ├── secrets
    |   └── mc-secret-1.enc.yaml
    └── organizations
        └── demo-gitops
            ├── demo-gitops.yaml
            ├── kustomization.yaml
            ├── namespace.yaml
            ├── namespace
            |   ├── kustomization.yaml
            |   ├── secrets
            |   |   ├── kustomization.yaml
            |   |   └── org-secret-1.enc.yaml
            |   └── workload-clusters
            |       ├── kustomization.yaml
            |       └── demo0.yaml
            └── workload-clusters
                └── demo0
```

Don't mix organizations, or workload clusters, with other resources in one directory. If there are no other
resources, you can leave the directory out and put the organizations or clusters right under their parent:

```text
management-clusters
└── demomc
    └── demo-gitops
        ├── demo-gitops.yaml
        ├── kustomization.yaml
        ├── namespace.yaml
        ├── namespace
        |   ├── kustomization.yaml
        |   └── demo0.yaml
        └── demo0
```

### The organisation's name

The organisation's name is set once, as the `metadata.name` of its `Organization` in `ORG_NAME.yaml`. The
organisation's `kustomization.yaml` lists `ORG_NAME.yaml`, `namespace.yaml` and `multicluster`, and its
`replacements` copy the name into what Flux applies from them:

- into `spec.postBuild.substitute.organization` of every Flux `Kustomization`, which the files they apply use as
  `${organization}`. Every Flux `Kustomization` in the organisation's build writes `organization`, as
  `organization: "ORG_NAME"` in this repository, and the replacement updates it. One without it fails the build,
  which names the field;
- into `spec.targetNamespace` of the `Kustomization` with the label `giantswarm.io/organization-namespace: "true"`,
  the one in `namespace.yaml`. It applies the organisation's `namespace` directory, so everything there goes into
  the organisation's namespace.

The files in `namespace` name no namespace: `targetNamespace` sets it. Where one needs the organisation's name as a
value, such as the namespace the Kyverno `Policy` in `namespace/workload-cluster-secret-stores` generates in, it writes
`${organization}`, which the `postBuild` of `namespace.yaml` fills in. So do the workload clusters' `Kustomization`s
in `namespace/workload-clusters`: `organization: "${organization}"`, and `org-${organization}` as the namespace of a
`Cluster` health check.

`org-ORG_NAME` is a fixed placeholder: write it as it is, and don't change it to your organisation's name. The
replacements keep `org-` and put the name after it, so `org-ORG_NAME` becomes `org-demo-gitops` for the organisation
`demo-gitops`. The replacements win over what the files say, so a hand-written `organization` or namespace that names
the organisation is updated to the `Organization`'s name.

A SOPS-encrypted Secret in `namespace` must name the real namespace, `org-<name>`, never the placeholder: changing the
encrypted file breaks its MAC, so Flux couldn't decrypt it. `targetNamespace` sets the same namespace, which keeps the
MAC intact.

If you don't want to use the replacements, leave them out of the organisation's `kustomization.yaml`, and replace
`ORG_NAME` and `org-ORG_NAME` with your organisation's name wherever they stand for it: in the multi-cluster apps
`Kustomization` in `multicluster/apps.yaml`, and in `namespace.yaml`. The files in `namespace` get the name from
`namespace.yaml`. The template's `kustomization.yaml` lists its own files of these kinds in a comment.

Flux applies the organisation's directory as its `kustomization.yaml` builds it, so list there everything else in the
directory that Flux has to apply in `default`. Put what belongs in the organisation's namespace, such as its
`secrets`, in `namespace` and list it in `namespace/kustomization.yaml`: `MC_NAME.yaml` applies only the
`Organization`s and objects in `default`, see [Flux Kustomizations](#flux-kustomizations). Build the organisation's
directory to see what `MC_NAME.yaml` applies, for example with
`kubectl kustomize management-clusters/MC_NAME/organizations/ORG_NAME`. Building `namespace` on its own leaves
`${organization}` as it is.

### `cluster`, `apps` and `[out-of-band]`

Every workload cluster directory holds the resources on the management cluster that configure the workload
cluster, through the Management API, in `cluster` and `apps`. Examples are the `HelmRelease` and
`OCIRepository` resources of the cluster and its apps, and the ConfigMaps and Secrets with their values. Its
`kustomization.yaml` lists the directories the cluster's Kustomizations apply, and never `out-of-band`, which must not
be applied to the management cluster.

The optional `out-of-band` directory holds resources that go straight into the workload cluster, such as extra
ConfigMaps, Secrets or Deployments that aren't delivered as an app. There are two ways to apply it:

- Run Flux in the workload cluster and point it at the `out-of-band` directory.
- Add another Flux Kustomization on the management cluster that uses the workload cluster's kubeconfig. That's the
  optional `WC_NAME-direct.yaml`, with its own `WC_NAME-direct.gpgkey.enc.yaml`. It lives in the namespace of the
  kubeconfig Secret, the organisation's, so it goes in `namespace/workload-clusters`, and its key Secret, which has to
  be in the same namespace, in `namespace/secrets`. The organisation's namespace `Kustomization` applies both.
  `namespace/secrets/kustomization.yaml` gives its Secrets the `kustomize.toolkit.fluxcd.io/prune: disabled`
  annotation and the `giantswarm.io/prevent-deletion` label, as the management cluster's `secrets/kustomization.yaml`
  does, see [Add an organization](../add_org.md). A legacy cluster's kubeconfig Secret is in `default`: its
  `-direct.yaml` goes in `workload-clusters`, with `namespace: default` and no `dependsOn`, listed in a
  `workload-clusters/kustomization.yaml` that the organisation's `kustomization.yaml` lists, and its key Secret in the
  management cluster's `secrets`.

  `sops` encrypts the key Secret with the first rule in `.sops.yaml` whose `path_regex` matches its file. The
  management cluster's rule for the workload clusters' keys in `namespace/secrets`, from
  [Add a new Management Cluster](../add_mc.md), matches the files that end in `.gpgkey.enc.yaml` or `.agekey.enc.yaml`
  and encrypts them with the master key, which `sops-gpg-master` holds for the organisation's namespace
  `Kustomization`. See [SOPS keys](./sops-keys.md#encryption-rules).

## Flux Kustomizations

Three kinds of Flux Kustomization apply the repository:

```text
management-clusters
└── MC_NAME
    ├── MC_NAME.yaml                        # applies MC_NAME/: Organizations and objects in default
    └── organizations
        └── ORG_NAME
            ├── kustomization.yaml          # sets the organisation's name in what's below
            ├── ORG_NAME.yaml
            ├── namespace.yaml              # applies namespace/ into org-ORG_NAME
            ├── namespace
            |   ├── secrets                 # the clusters' SOPS keys
            |   └── workload-clusters
            |       ├── kustomization.yaml
            |       ├── WC_NAME.yaml            # applies WC_NAME/cluster/
            |       ├── WC_NAME-apps.yaml       # applies WC_NAME/, once the cluster is ready
            |       └── [WC_NAME-direct.yaml]   # applies WC_NAME/out-of-band/ to the workload cluster
            └── workload-clusters
                └── WC_NAME
                    ├── kustomization.yaml  # lists apps, not cluster or out-of-band
                    ├── apps                # the secondary apps
                    ├── cluster
                    |   ├── kustomization.yaml
                    |   └── [apps]          # the base apps
                    └── [out-of-band]       # applied only by the out-of-band mechanisms
```

`MC_NAME.yaml` applies only the `Organization`s and objects in `default`, the Flux Kustomizations among them. On a new
management cluster, no organisation's namespace exists until organization-operator creates it for the `Organization`.
Flux dry-runs every object of a `Kustomization` before it applies any, so one object in a missing namespace would stop
the `Organization` from being applied at all. Everything the organisation keeps in its namespace is in its `namespace`
directory instead, which the organisation's own `Kustomization`, `namespace.yaml`, applies with
`targetNamespace: org-ORG_NAME`. It fails until the namespace exists, then succeeds on its next retry, a minute later:
nothing else waits for the namespace, and there's no health check. Its `dependsOn` names `MC_NAME.yaml`'s
`Kustomization`. Both read the same `GitRepository`, so Flux applies a commit to the organisation's namespace only once
`MC_NAME.yaml` is `Ready` at the same revision: `MC_NAME.yaml` always applies a commit first. The namespace
`Kustomization`'s own spec, such as its `path` or `targetNamespace`, is up to date before it applies the commit, and an
object that moves between the two in one commit moves in that order. `MC_NAME.yaml` has no `wait` and no health
checks, so it never waits for the organisations. A broken file in one organisation's `namespace` stops only that
organisation's `Kustomization`, not `MC_NAME.yaml` or the other organisations; while `MC_NAME.yaml` fails, the
organisations' `Kustomization`s report `DependencyNotReady` and apply nothing new.

The workload clusters' Kustomizations are in the organisation's `namespace/workload-clusters`, so `namespace.yaml`
creates them in the organisation's namespace, and not the cluster directories, which they apply. In that namespace:

- `serviceAccountName: automation` is the organisation's `automation` ServiceAccount. rbac-operator gives it every
  right in the organisation's namespace and lets it write nowhere else, so a cluster directory may hold only objects
  in that namespace: one that applies an object in `default`, in another namespace or a cluster-scoped one fails with
  "forbidden". Put those in what `MC_NAME.yaml` applies.
- `decryption.secretRef` names a key Secret in the organisation's namespace, in `namespace/secrets`.
- `sourceRef` names the repository's `GitRepository` with `namespace: default`, where it is.
- `dependsOn` names `namespace.yaml`'s `Kustomization`, `{name: MC_NAME-organization-ORG_NAME, namespace: default}`,
  in every one that doesn't depend on another of them, such as the cluster's own. Both read the same `GitRepository`,
  so `namespace.yaml` applies every commit first, as `MC_NAME.yaml` does before it: a cluster `Kustomization`'s own
  spec, such as a new `postBuild` variable, is up to date before it applies the commit. While `MC_NAME.yaml` or the
  organisation's `namespace.yaml` fails, the organisation's clusters report `DependencyNotReady` and apply nothing new.

They set the variables, like `${cluster_name}`, that the bases use. Their `organization` is `${organization}`, which
the `postBuild` of `namespace.yaml` fills in, see [The organisation's name](#the-organisations-name). See
[How it works](../how-it-works.md) for why the management cluster's and the clusters' Kustomizations are separate.

In the same way, the `kustomization.yaml` in `multicluster` lists only `apps.yaml`, whose Kustomization applies the
organisation's apps on several clusters in `multicluster/apps`, so the management cluster's Kustomization never applies
their `ResourceSet`s itself. See [Apps on several clusters](../guides/scheduled-updates.md#apps-on-several-clusters).

A cluster with apps has two Kustomizations:

1. `WC_NAME.yaml` applies `cluster`: the cluster's `HelmRelease` and its base apps, in `cluster/apps`. Base apps are the
   ones the cluster needs from the start, such as the Gateway API charts of the
   [envoy-gateway](/bases/stacks/envoy-gateway/) stack in the out-of-band examples. Flux applies them with the cluster,
   and their `HelmRelease`s install them as soon as the cluster can take them. The Kustomization's `healthChecks` name
   the Cluster API `Cluster` the chart creates, and its `healthCheckExprs` count it as ready once its `Available`
   condition is `True`. The Kustomization only gets `Ready` then, so its `timeout` of 30 minutes covers a new cluster
   coming up. While the cluster isn't `Available`, each reconciliation waits for up to those 30 minutes: a change you
   push to the cluster's files, such as a fix to its values, is only applied after the wait runs out, and the apps
   Kustomization reports `DependencyNotReady` all the while.
1. `WC_NAME-apps.yaml` applies the cluster's directory: the secondary apps in `apps`, which its `kustomization.yaml`
   lists. It has the cluster's Kustomization in `dependsOn`, so Flux applies none of them until the cluster is
   `Available`. Until then, it reports `DependencyNotReady`.

Name the cluster in `healthChecks` with its name written out, such as `capi-wc-name`, and the namespace as
`org-${organization}`. Flux doesn't substitute variables in a `Kustomization`'s own spec, but `namespace.yaml`, which
applies it, fills in `${organization}`. The namespace must be explicit: Flux doesn't default it to the
`Kustomization`'s. A cluster without secondary apps, such as the `HELLO_APP_*` examples, has only `WC_NAME.yaml`, which
applies the cluster's directory, whose `kustomization.yaml` lists `cluster`, and needs no health check.

`kubectl gs gitops add workload-cluster` still generates a `mapi` directory, with `cluster` and `apps` in it, and a
single `WC_NAME.yaml` that applies all of `mapi`, so its apps don't wait for the cluster. It writes that file into the
organisation's `workload-clusters`, in `default`, and lists it in `workload-clusters/kustomization.yaml`, which it
needs. Move the contents of `mapi` up into the cluster's directory, take one `../` off the paths to the bases in
`cluster/kustomization.yaml`, which it writes for `mapi/cluster`, add the cluster's `kustomization.yaml`, and split
the Kustomization as above, into `namespace/workload-clusters`, with the fields above. Then delete the CLI's file and
`workload-clusters/kustomization.yaml`. Don't use `kubectl gs gitops add encryption --workload-cluster` on structure
version 3: it writes the cluster's key Secret into `MC_NAME/secrets`, in `default`, and edits
`workload-clusters/WC_NAME.yaml`, which no longer exists. Create the key as
[Add a new Workload Cluster repository structure](../add_wc_structure.md) describes instead.

### Reconcile intervals

A change doesn't wait for the `Kustomization` or `HelmRelease` intervals. Flux applies a new commit as soon as the
`GitRepository` has fetched it, installs a new chart as soon as its `OCIRepository` has, and applies a change to a
values ConfigMap or Secret at once, as they carry the `reconcile.fluxcd.io/watch: Enabled` label. The intervals set
how often Flux checks a source for changes, and how often it reapplies what hasn't changed, to undo drift:

| Object | `interval` | `retryInterval` | Why |
| --- | --- | --- | --- |
| `GitRepository` | 1m | | How soon Flux sees a push. A [`Receiver`][flux-receiver] makes it immediate. |
| Management cluster `Kustomization`, `MC_NAME.yaml` | 10m | 1m | Only undoes drift, the same as `flux bootstrap` sets. It also applies the Organizations. |
| Organisation namespace `Kustomization`, `namespace.yaml` | 10m | 1m | The retry applies it a minute after organization-operator has created the namespace. |
| Workload cluster `Kustomization`s, `WC_NAME.yaml`, `WC_NAME-apps.yaml`, `-direct` and `HELLO_APP_*` | 10m | 1m | One to three per cluster, each building and applying its whole directory. |
| `OCIRepository` | 10m | | How soon a `semver` range picks up a new chart. |
| `HelmRelease` | 5m | | Checks the Helm release and remediates a failed one, without building anything. |

`retryInterval` retries a failed `Kustomization` after a minute instead of the next `interval`. An apps `Kustomization`
whose cluster isn't ready yet checks again every 30 seconds whatever its interval, as `dependsOn` does.

[flux-receiver]: https://fluxcd.io/flux/components/notification/receivers/
