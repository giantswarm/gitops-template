This page lists the directories and files of the repository and the rules for them. For how Flux turns them into
clusters, see [How it works](../explanation/how-it-works.md).

## Layout

The repository follows the hierarchy of the platform: a management cluster has organisations, and an organisation
has workload clusters.

```text
.sops.yaml
bases
├── apps                                                App Templates, see tutorials/intermediate/app-templates.md
├── clusters                                            cluster bases, see tutorials/intermediate/cluster-bases.md
|   ├── PROVIDER                                        a provider's base, such as capa
|   └── [BASE_NAME]                                     a cluster base built on a provider's base
├── environments                                        stages and regions, see tutorials/intermediate/stages-and-regions.md
├── secret_stores                                       SecretStores for a secret manager, see how-to/external-secrets.md
├── shared_objects                                      objects every organisation gets, see how-to/share-objects.md
└── stacks                                              several apps deployed together, see tutorials/intermediate/stacks.md
management-clusters
└── MC_NAME
    ├── .sops.keys
    ├── [kustomization.yaml]
    ├── [OTHER_RESOURCES]
    ├── [notifications]                                 commit statuses, see how-to/commit-statuses.md
    ├── secrets
    |   └── MC_NAME.gpgkey.enc.yaml
    ├── MC_NAME.yaml
    └── [organizations]
        ├── [kustomization.yaml]
        └── ORG_NAME
            ├── kustomization.yaml                      sets the organisation's name, see below
            ├── [OTHER_RESOURCES]                       in `default`
            ├── ORG_NAME.yaml
            ├── namespace.yaml                          applies namespace/ into the organisation's namespace
            ├── namespace                               namespace.yaml responsibility, never MC_NAME.yaml's
            |   ├── kustomization.yaml
            |   ├── [OTHER_RESOURCES]                   in the organisation's namespace
            |   ├── [secrets]                           kept by Flux, as MC_NAME's secrets are
            |   |   ├── kustomization.yaml
            |   |   ├── [WC_NAME.gpgkey.enc.yaml]       a workload cluster's SOPS key
            |   |   └── [WC_NAME-direct.gpgkey.enc.yaml]
            |   ├── [notifications]                     the organisation's commit statuses
            |   └── [shared-objects]                    objects every organisation shares, see how-to/share-objects.md
            ├── [multicluster]                          apps on several clusters, see tutorials/advanced/multicluster-apps.md
            |   ├── kustomization.yaml
            |   ├── apps.yaml
            |   ├── apps                                apps.yaml responsibility
            |   |   ├── kustomization.yaml
            |   |   ├── clusters.yaml
            |   |   └── APP_NAME
            |   └── [secret-stores]                     a SecretStore for every workload cluster, generated by
            |                                           Kyverno; namespace.yaml responsibility
            └── [workload-clusters]                     namespace.yaml responsibility
                ├── kustomization.yaml
                ├── WC_NAME.yaml
                ├── [WC_NAME-apps.yaml]
                ├── [WC_NAME-direct.yaml]
                └── WC_NAME                             managed from WC_NAME.yaml and WC_NAME-apps.yaml
-----------------------------------------------------------------------------------
                    ├── kustomization.yaml                WC_NAME.yaml responsibility
                    ├── apps
                    ├── cluster
                    ├── [out-of-band]
                    |   ├── [kustomization.yaml]
                    |   └── [OTHER_RESOURCES]
                    └── [teams]                           application teams' repositories, see tutorials/advanced/teams.md
```

How to read it:

- Names in capital letters are placeholders. Replace them with your own names, following the [naming](#naming) rules.
  Lowercase parts stay as they are: `WC_NAME-apps.yaml` for a cluster `demo0` is `demo0-apps.yaml`.
- Names with an extension, like `MC_NAME.yaml`, are files. The rest are directories.
- Names in square brackets are optional. See [optional components](#optional-components).
- The horizontal line splits the work between the [Flux Kustomizations](#flux-kustomizations). `MC_NAME.yaml`
  applies everything above it but what the organisation's `namespace/kustomization.yaml` lists: `namespace`,
  `../multicluster/secret-stores` and `../workload-clusters`, which `namespace.yaml` applies into the organisation's
  namespace. The cluster's Kustomizations, in `workload-clusters`, apply the cluster directory below it, except
  `out-of-band`.
- `.sops.yaml`, `.sops.keys` and the `*.gpgkey.enc.yaml` files are only needed when you encrypt secrets with SOPS.
  See [SOPS keys](./sops-keys.md).

The example directories under [management-clusters/MC_NAME](/management-clusters/MC_NAME/) and [bases](/bases/) each
explain what they show and what to change when you copy them.

### What kubectl-gs writes

`kubectl gs gitops` writes some of these files, in the names this page uses. The rest you write by hand, from the
docs or by copying an example. The commands write the layout of [structure version](#structure-version) 2, so most
of what they write needs a few changes, which [Let kubectl-gs write the files](../how-to/kubectl-gs.md) lists.

| Directory or file | Written by |
| --- | --- |
| `.gitops-metadata.yaml`, `.sops.yaml` | `kubectl gs gitops init`; every `add` command records its layer in `.gitops-metadata.yaml` |
| `MC_NAME/MC_NAME.yaml`, `MC_NAME/organizations` | `kubectl gs gitops add management-cluster` |
| `MC_NAME/.sops.keys`, `MC_NAME/secrets/MC_NAME.gpgkey.enc.yaml` | `kubectl gs gitops add management-cluster --gen-master-key`, or by hand |
| `MC_NAME/secrets/kustomization.yaml` | by hand |
| `ORG_NAME/ORG_NAME.yaml`, `ORG_NAME/workload-clusters/kustomization.yaml` | `kubectl gs gitops add organization` |
| `ORG_NAME/kustomization.yaml`, `ORG_NAME/namespace.yaml`, `ORG_NAME/namespace` | by hand |
| `ORG_NAME/multicluster` | by hand |
| `WC_NAME.yaml`, `WC_NAME/cluster` | `kubectl gs gitops add workload-cluster`, in `mapi/cluster` unless you pass `--skip-mapi` |
| `WC_NAME-apps.yaml`, `WC_NAME-direct.yaml`, `WC_NAME/kustomization.yaml` | by hand |
| `WC_NAME/cluster/cluster_userconfig.yaml`, `WC_NAME/cluster/patch_cluster_userconfig.yaml` | `kubectl gs gitops add workload-cluster --cluster-user-config` |
| `WC_NAME/apps/kustomization.yaml` | `kubectl gs gitops add workload-cluster` |
| `WC_NAME/apps/patch_cluster_config.yaml` | by hand |
| `WC_NAME/apps/APP_NAME` | `kubectl gs gitops add app`, which is deprecated, or by hand |
| `WC_NAME/out-of-band`, `WC_NAME/teams` | by hand |
| A workload cluster's SOPS key and its rule in `.sops.yaml` | by hand, see [Keep secrets in the repository](../how-to/sops.md); `kubectl gs gitops add encryption` writes the key where this layout can't use it |
| `bases/clusters/PROVIDER` | `kubectl gs gitops add base --provider PROVIDER`, in `bases/clusters/PROVIDER/template` |
| `bases/clusters/BASE_NAME`, `bases/apps`, `bases/stacks`, `bases/environments`, `bases/secret_stores`, `bases/shared_objects` | by hand |
| An app's version range, `spec.ref.semver` in its `oci-repository.yaml` | `kubectl gs gitops add automatic-update`, or by hand |

## Structure version

The structure on this page has a version, so a repository built on it can tell when it has fallen behind. The
current structure version is `3`. It goes up when an existing repository has to change to follow the structure, for
example when a directory moves or a naming rule changes. New examples and changes to the apps under `bases/` don't
change it.

`kubectl gs gitops` records the version in a `.gitops-metadata.yaml` file at the root of the repository, with an
entry for every management cluster, organisation, workload cluster, app and base it created:

```yaml
apiVersion: gitops.giantswarm.io/v1alpha1
kind: RepositoryMetadata
structureVersion: 3
layers:
  - kind: management-cluster
    path: management-clusters/MC_NAME
    structureVersion: 3
```

The file sits outside of what Flux applies, so it never reaches a cluster. Don't edit it by hand.

| Version | What it brought | Written by |
| --- | --- | --- |
| 1 | Clusters and apps as App CRs | kubectl-gs before 6.0.0 |
| 2 | Clusters and apps as Flux `HelmRelease`s, in a workload cluster's `mapi` directory | kubectl-gs 6.0.0 and newer |
| 3 | No `mapi`; an organisation's `namespace` directory and `namespace.yaml`; the workload clusters' Kustomizations and keys in the organisation's namespace | no kubectl-gs release yet |

To check which parts of your repository are behind and bring them up to date, see
[Check and upgrade the structure version](../how-to/upgrade-fork.md#check-and-upgrade-the-structure-version).

## Naming

| Placeholder | Rule |
| --- | --- |
| `MC_NAME` | The management cluster's codename |
| `ORG_NAME` | The organisation's name, in lowercase and without the `org-` prefix |
| `WC_NAME` | Any name, but the workload cluster's name is clearest |
| `PROVIDER` | The Cluster API provider, such as `capa`, as `kubectl gs gitops add base --provider` names it |
| `BASE_NAME` | Any name other than a provider's, such as `my-defaults` |

Files and resources use the names `kubectl gs gitops` generates, so it recognises them in `gitops check`,
`gitops upgrade` and `gitops add automatic-update`:

| What | Name |
| --- | --- |
| Management cluster Flux `Kustomization` | `MC_NAME-gitops`, in `MC_NAME.yaml` |
| Workload cluster Flux `Kustomization` | `MC_NAME-clusters-WC_NAME`, in `WC_NAME.yaml` |
| Flux `Kustomization` of a workload cluster's secondary apps | `MC_NAME-clusters-WC_NAME-apps`, in `WC_NAME-apps.yaml`. `kubectl gs gitops` doesn't generate it, see [Flux Kustomizations](#flux-kustomizations) |
| An app's `HelmRelease` and `OCIRepository` when it's a base app, installed with the cluster | the same files, in `cluster/apps/APP_NAME` |
| Out-of-band Flux `Kustomization` on the management cluster, which applies `out-of-band` through the workload cluster's kubeconfig | `MC_NAME-clusters-WC_NAME-direct`, in `WC_NAME-direct.yaml`. `kubectl gs gitops` doesn't generate it |
| Flux `Kustomization` of an organisation's namespace | `MC_NAME-organization-ORG_NAME`, in `namespace.yaml`. `kubectl gs gitops` doesn't generate it |
| Flux `Kustomization` of an organisation's apps on several clusters | `MC_NAME-multicluster-apps-ORG_NAME`, in `multicluster/apps.yaml`. `kubectl gs gitops` doesn't generate it |
| An app's `HelmRelease` and `OCIRepository` | `helm-release.yaml` and `oci-repository.yaml`, one resource each, in `apps/APP_NAME` |
| An app's values for one cluster | `override_config.yaml`, which the app's `kustomization.yaml` turns into the `${cluster_name}-APP_NAME-user-values` ConfigMap, and `secret.enc.yaml` with the `${cluster_name}-APP_NAME-user-secrets` Secret, see [App values](./values.md#app-values) |
| A workload cluster's values | `cluster_userconfig.yaml` with the `${cluster_name}-cluster-userconfig` ConfigMap, in `cluster` |
| The patch that adds them to the cluster's `HelmRelease` | `patch_cluster_userconfig.yaml`, in `cluster` |
| A workload cluster's region | a `components:` entry for `bases/environments/regions/REGION`, in `cluster/kustomization.yaml`. Every cluster needs one, or it would be created in the management cluster's region and CI fails, see [Regions](../tutorials/intermediate/stages-and-regions.md#regions). `kubectl gs gitops` doesn't generate it |
| A workload cluster's stage | a `components:` entry for `bases/environments/stages/STAGE`, in `cluster/kustomization.yaml`, optional, see [Stages](../tutorials/intermediate/stages-and-regions.md#stages). `kubectl gs gitops` doesn't generate it |
| A provider's cluster base | `cluster.yaml`, `cluster_config.yaml` and `kustomization.yaml`, in `bases/clusters/PROVIDER` |
| A cluster base built on a provider's base | `kustomization.yaml` and its own files, in `bases/clusters/BASE_NAME`, next to the provider's base and never inside it, see [Cluster bases](../tutorials/intermediate/cluster-bases.md) |
| A stack, several apps deployed together | `kustomization.yaml` and a values file per app, in `bases/stacks/STACK_NAME`, see [Stacks](../tutorials/intermediate/stacks.md). `kubectl gs gitops` doesn't generate it |

The suffixes the template adds to file and object names that `kubectl gs gitops` doesn't generate, such as `-apps`,
`-direct` and the `-from-template` of the example apps, are only the template's labels for telling its techniques apart.
They aren't a convention, and nothing relies on them: name your own files and objects however you like. The same goes
for out-of-band delivery, which has two forms, and the template shows both: a `Kustomization` on the management cluster
that applies `out-of-band` through the workload cluster's kubeconfig, the template's `-direct` one, and Flux in the
workload cluster pulling the same content itself, see
[Apply resources straight to a workload cluster](../tutorials/advanced/out-of-band.md).

Repositories forked before the template used these names can move to them with
[Move to the kubectl-gs names](../how-to/upgrade-fork.md#move-to-the-kubectl-gs-names).

## Optional components

### `[OTHER_RESOURCES]`

These are any other Kubernetes resources you add, as files or directories, at the level they belong to. When you
have more than a few, group them by kind:

```text
management-clusters
└── demomc
    ├── secrets
    |   ├── secret-1.enc.yaml
    |   └── secret-2.enc.yaml
    └── configmaps
        └── cm.yaml
```

### `[kustomization.yaml]`

If a directory has no `kustomization.yaml`, Flux generates one that includes every file in it and in its
subdirectories, until it finds a `kustomization.yaml`. Add one when you want to list the resources yourself or use
other [kustomize features](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/#kustomize-feature-list).

If you add one, include this option. It records in every resource the file it came from, which makes debugging
easier:

```yaml
buildMetadata: [originAnnotations]
```

### `[organizations]` and `[workload-clusters]`

These directories keep the organisations apart from the management cluster's other resources, and the workload
clusters apart from the organisation's other resources. Use them when there are other resources at the same level:

```text
management-clusters
└── demomc
    ├── secrets
    |   └── mc-secret-1.enc.yaml
    └── organizations
        └── demo-gitops
            ├── demo-gitops.yaml
            ├── kustomization.yaml
            ├── namespace.yaml
            ├── namespace
            |   ├── kustomization.yaml              lists secrets and ../workload-clusters
            |   └── secrets
            |       ├── kustomization.yaml
            |       └── org-secret-1.enc.yaml
            └── workload-clusters
                ├── kustomization.yaml
                ├── demo0.yaml
                └── demo0
```

Don't mix organisations, or workload clusters, with other resources in one directory. If there are no other
resources, you can leave the directory out and put the organisations or clusters right under their parent:

```text
management-clusters
└── demomc
    └── demo-gitops
        ├── demo-gitops.yaml
        ├── kustomization.yaml
        ├── namespace.yaml
        ├── namespace
        |   └── kustomization.yaml              lists ../demo0.yaml
        ├── demo0.yaml
        └── demo0
```

### The organisation's name

The organisation's name is set once, as the `metadata.name` of its `Organization` in `ORG_NAME.yaml`. The
organisation's `kustomization.yaml` lists `ORG_NAME.yaml`, `namespace.yaml` and `multicluster`, and its
`replacements` copy the name into what Flux applies from them:

- into `spec.postBuild.substitute.organization` of every Flux `Kustomization`, which the files they apply use as
  `${organization}`. Every Flux `Kustomization` in the organisation's build writes `organization`, as
  `organization: "ORG_NAME"` in this repository, and the replacement updates it. One without it fails the build,
  which names the field;
- into `spec.targetNamespace` of the `Kustomization` with the label `giantswarm.io/organization-namespace: "true"`,
  the one in `namespace.yaml`. It applies the organisation's `namespace` directory, so everything it lists goes into
  the organisation's namespace: what's in `namespace`, `../workload-clusters` and `../multicluster/secret-stores`.

The files it applies name no namespace: `targetNamespace` sets it. Where one needs the organisation's name as a value,
such as the namespace the Kyverno `Policy` in `multicluster/secret-stores` generates in, it writes `${organization}`,
which the `postBuild` of `namespace.yaml` fills in. So do the workload clusters' `Kustomization`s in
`workload-clusters`: `organization: "${organization}"`, and `org-${organization}` as the namespace of a `Cluster`
health check.

`org-ORG_NAME` is a fixed placeholder: write it as it is, and don't change it to your organisation's name. The
replacements keep `org-` and put the name after it, so `org-ORG_NAME` becomes `org-demo-gitops` for the organisation
`demo-gitops`. The replacements win over what the files say, so a hand-written `organization` or namespace that names
the organisation is updated to the `Organization`'s name.

A SOPS-encrypted Secret in `namespace` names the real namespace, `org-<name>`, never the placeholder, and you write it
before you encrypt the file. The namespace stays in clear text in the encrypted file, but SOPS covers it with the
file's MAC all the same. Change the file after encrypting it, by hand or with a search-and-replace when you copy an
organisation, and the MAC no longer matches: `sops` then refuses to decrypt the file in place to change it, and you
can't rotate its key either. The only way out is to delete the Secret and create it again. Flux doesn't check the MAC
when it decrypts, which is why `targetNamespace`, and the labels and annotations kustomize adds while it builds, do no
harm: they change what Flux applies, not the file in Git.

If you don't want to use the replacements, leave them out of the organisation's `kustomization.yaml`, and replace
`ORG_NAME` and `org-ORG_NAME` with your organisation's name wherever they stand for it: in the multi-cluster apps
`Kustomization` in `multicluster/apps.yaml`, and in `namespace.yaml`. The files in `namespace` get the name from
`namespace.yaml`. The template's `kustomization.yaml` lists its own files of these kinds in a comment.

Flux applies the organisation's directory as its `kustomization.yaml` builds it, so list there everything else in the
directory that Flux has to apply in `default`. Put what belongs in the organisation's namespace, such as its
`secrets`, in `namespace` and list it in `namespace/kustomization.yaml`: `MC_NAME.yaml` applies only the
`Organization`s and objects in `default`, see [Flux Kustomizations](#flux-kustomizations). Build the organisation's
directory to see what `MC_NAME.yaml` applies, for example with
`kubectl kustomize management-clusters/MC_NAME/organizations/ORG_NAME`. Building `namespace` on its own leaves
`${organization}` as it is.

### `cluster`, `apps` and `[out-of-band]`

Every workload cluster directory holds the resources on the management cluster that configure the workload
cluster, through the Management API, in `cluster` and `apps`. Examples are the `HelmRelease` and
`OCIRepository` resources of the cluster and its apps, and the ConfigMaps and Secrets with their values. Its
`kustomization.yaml` lists the directories the cluster's Kustomizations apply, and never `out-of-band`, which must not
be applied to the management cluster.

The optional `out-of-band` directory holds resources that go straight into the workload cluster, such as extra
ConfigMaps, Secrets or Deployments that aren't delivered as an app. There are two ways to apply it, which
[Apply resources straight to a workload cluster](../tutorials/advanced/out-of-band.md) walks through:

- Run Flux in the workload cluster and point it at the `out-of-band` directory.
- Add another Flux Kustomization on the management cluster that uses the workload cluster's kubeconfig. That's the
  optional `WC_NAME-direct.yaml`, with its own `WC_NAME-direct.gpgkey.enc.yaml`. It lives in the namespace of the
  kubeconfig Secret, the organisation's, where the organisation's namespace `Kustomization` puts it from
  `workload-clusters`, and its key Secret, which has to be in the same namespace, goes in `namespace/secrets`.
  `namespace/secrets/kustomization.yaml` gives its Secrets the `kustomize.toolkit.fluxcd.io/prune: disabled`
  annotation and the `giantswarm.io/prevent-deletion` label, as the management cluster's `secrets/kustomization.yaml`
  does, see [Add a workload cluster key (GPG)](../how-to/sops.md#add-a-workload-cluster-key-gpg).

  `sops` encrypts the key Secret with the first rule in `.sops.yaml` whose `path_regex` matches its file. The
  management cluster's rule for the workload clusters' keys in `namespace/secrets`, from
  [Connect the management cluster](../tutorials/basic/getting-started.md#1-connect-the-management-cluster), matches
  the files that end in `.gpgkey.enc.yaml` or `.agekey.enc.yaml` and encrypts them with the master key, which
  `sops-gpg-master` holds for the organisation's namespace `Kustomization`. See
  [SOPS keys](./sops-keys.md#encryption-rules).

## Flux Kustomizations

Three kinds of Flux Kustomization apply the repository:

```text
management-clusters
└── MC_NAME
    ├── MC_NAME.yaml                        # applies MC_NAME/: Organizations and objects in default
    └── organizations
        └── ORG_NAME
            ├── kustomization.yaml          # sets the organisation's name in what's below
            ├── ORG_NAME.yaml
            ├── namespace.yaml              # applies what namespace/ lists into org-ORG_NAME
            ├── namespace
            |   ├── kustomization.yaml      # lists secrets and ../workload-clusters
            |   └── secrets                 # the clusters' SOPS keys
            └── workload-clusters
                ├── kustomization.yaml
                ├── WC_NAME.yaml            # applies WC_NAME/cluster/
                ├── WC_NAME-apps.yaml       # applies WC_NAME/, once the cluster is ready
                ├── [WC_NAME-direct.yaml]   # applies WC_NAME/out-of-band/ to the workload cluster
                └── WC_NAME
                    ├── kustomization.yaml  # lists apps, not cluster or out-of-band
                    ├── apps                # the secondary apps
                    ├── cluster
                    |   ├── kustomization.yaml
                    |   └── [apps]          # the base apps
                    └── [out-of-band]       # applied only by the out-of-band mechanisms
```

`MC_NAME.yaml` applies only the `Organization`s and objects in `default`, the Flux Kustomizations among them. On a new
management cluster, no organisation's namespace exists until organization-operator creates it for the `Organization`.
Flux dry-runs every object of a `Kustomization` before it applies any, so one object in a missing namespace would stop
the `Organization` from being applied at all. Everything the organisation keeps in its namespace is what its
`namespace/kustomization.yaml` lists instead, which the organisation's own `Kustomization`, `namespace.yaml`, applies
with `targetNamespace: org-ORG_NAME`. It fails until the namespace exists, then succeeds on its next retry, a minute
later: nothing else waits for the namespace, and there's no health check. Its `dependsOn` names `MC_NAME.yaml`'s
`Kustomization`. Both read the same `GitRepository`, so Flux applies a commit to the organisation's namespace only once
`MC_NAME.yaml` is `Ready` at the same revision: `MC_NAME.yaml` always applies a commit first. The namespace
`Kustomization`'s own spec, such as its `path` or `targetNamespace`, is up to date before it applies the commit, and an
object that moves between the two in one commit moves in that order. `MC_NAME.yaml` has no `wait` and no health
checks, so it never waits for the organisations. A broken file in one organisation's `namespace` stops only that
organisation's `Kustomization`, not `MC_NAME.yaml` or the other organisations; while `MC_NAME.yaml` fails, the
organisations' `Kustomization`s report `DependencyNotReady` and apply nothing new.

The workload clusters' Kustomizations are in the organisation's `workload-clusters`, next to the cluster directories
they apply. `namespace/kustomization.yaml` lists `../workload-clusters`, and `workload-clusters/kustomization.yaml`
lists only the Kustomization files, so `namespace.yaml` creates them in the organisation's namespace, and not the
cluster directories. In that namespace:

- `serviceAccountName: automation` is the organisation's `automation` ServiceAccount. rbac-operator gives it every
  right in the organisation's namespace and lets it write nowhere else, so a cluster directory may hold only objects
  in that namespace: one that applies an object in `default`, in another namespace or a cluster-scoped one fails with
  "forbidden". Put those in what `MC_NAME.yaml` applies.
- `decryption.secretRef` names a key Secret in the organisation's namespace, in `namespace/secrets`.
- `sourceRef` names the repository's `GitRepository` with `namespace: default`, where it is.
- `dependsOn` names `namespace.yaml`'s `Kustomization`, `{name: MC_NAME-organization-ORG_NAME, namespace: default}`,
  in every one that doesn't depend on another of them, such as the cluster's own. Both read the same `GitRepository`,
  so `namespace.yaml` applies every commit first, as `MC_NAME.yaml` does before it: a cluster `Kustomization`'s own
  spec, such as a new `postBuild` variable, is up to date before it applies the commit. While `MC_NAME.yaml` or the
  organisation's `namespace.yaml` fails, the organisation's clusters report `DependencyNotReady` and apply nothing new.

They set the [variables](#variables), like `${cluster_name}`, that the bases use. Their `organization` is
`${organization}`, which the `postBuild` of `namespace.yaml` fills in, see
[The organisation's name](#the-organisations-name). See
[How it works](../explanation/how-it-works.md#from-a-commit-to-a-cluster) for why the management cluster's and the
clusters' Kustomizations are separate.

In the same way, the `kustomization.yaml` in `multicluster` lists only `apps.yaml`, whose Kustomization applies the
organisation's apps on several clusters in `multicluster/apps`, so the management cluster's Kustomization never applies
their `ResourceSet`s itself. Like `namespace.yaml`, it depends on `MC_NAME.yaml`'s `Kustomization`, which applies every
commit first. See [Roll an app out to many clusters](../tutorials/advanced/multicluster-apps.md).

A cluster with apps has two Kustomizations:

1. `WC_NAME.yaml` applies `cluster`: the cluster's `HelmRelease` and its base apps, in `cluster/apps`. Base apps are the
   ones the cluster needs from the start, such as the Gateway API charts of the
   [envoy-gateway](/bases/stacks/envoy-gateway/) stack in the out-of-band examples. Flux applies them with the cluster,
   and their `HelmRelease`s install them as soon as the cluster can take them. The Kustomization's `healthChecks` name
   the Cluster API `Cluster` the chart creates, and its `healthCheckExprs` count it as ready once its
   `ControlPlaneAvailable` and `RemoteConnectionProbe` conditions are `True`: the control plane is up and the
   management cluster can reach it, which is all the apps need to install. The Kustomization only gets `Ready` then,
   so its `timeout` of 30 minutes covers a new cluster coming up. While the control plane isn't up, each
   reconciliation waits for up to those 30 minutes: a change you push to the cluster's files, such as a fix to its
   values, is only applied after the wait runs out, and the apps Kustomization reports `DependencyNotReady` all the
   while. The check doesn't wait for the cluster's `Available` condition, which also counts every node pool: with it,
   one node pool short of its minimum would hold back every change to the cluster's apps, including the one that
   would fix it. Cluster API keeps `ControlPlaneAvailable` `True` through a rolling upgrade of the control plane while
   enough of it is healthy, and reports `RemoteConnectionProbe` `False` only once the cluster has been unreachable for
   50 seconds. On a new cluster, the control plane can be up before any worker node has joined, so the secondary apps'
   pods may wait `Pending`, and a `HelmRelease` may run out its 10-minute `timeout`. The app bases retry a failed
   install up to 10 times, uninstalling it in between, so it settles by itself once the nodes join. A slower first
   install is the price of not holding back every later change to the apps while one node pool is short.
1. `WC_NAME-apps.yaml` applies the cluster's directory: the secondary apps in `apps`, which its `kustomization.yaml`
   lists. It has the cluster's Kustomization in `dependsOn`, so Flux applies none of them until the cluster's control
   plane is up. Until then, it reports `DependencyNotReady`.

Name the cluster in `healthChecks` with its name written out, such as `capi-wc-name`, and the namespace as
`org-${organization}`. Flux doesn't substitute variables in a `Kustomization`'s own spec, but `namespace.yaml`, which
applies it, fills in `${organization}`. The namespace must be explicit: Flux doesn't default it to the
`Kustomization`'s. A cluster without secondary apps, such as the `HELLO_APP_*` examples, has only `WC_NAME.yaml`, which
applies the cluster's directory, whose `kustomization.yaml` lists `cluster`, and needs no health check.

`kubectl gs gitops add workload-cluster` writes a single `WC_NAME.yaml` in `default` that applies the whole cluster
directory, so its apps don't wait for the cluster, and a `mapi` directory unless you pass `--skip-mapi`.
`kubectl gs gitops add encryption --workload-cluster` writes the cluster's key Secret into `MC_NAME/secrets`, in
`default`, where the cluster's Kustomizations can't read it. [Workload cluster](../how-to/kubectl-gs.md#workload-cluster)
lists what to change in what they write.

### Reconcile intervals

A change doesn't wait for the `Kustomization` or `HelmRelease` intervals. Flux applies a new commit as soon as the
`GitRepository` has fetched it, installs a new chart as soon as its `OCIRepository` has, and applies a change to a
values ConfigMap or Secret at once, as they carry the `reconcile.fluxcd.io/watch: Enabled` label. The intervals set
how often Flux checks a source for changes, and how often it reapplies what hasn't changed, to undo drift on the
management cluster:

| Object | `interval` | `retryInterval` | Why |
| --- | --- | --- | --- |
| `GitRepository` | 1m | | How soon Flux sees a push. A [`Receiver`][flux-receiver] makes it immediate. |
| Management cluster `Kustomization`, `MC_NAME.yaml` | 10m | 1m | Only undoes drift, the same as `flux bootstrap` sets. It also applies the Organizations. |
| Organisation namespace `Kustomization`, `namespace.yaml` | 10m | 1m | The retry applies it a minute after organization-operator has created the namespace. |
| Workload cluster `Kustomization`s, `WC_NAME.yaml`, `WC_NAME-apps.yaml`, `-direct` and `HELLO_APP_*` | 10m | 1m | One to three per cluster, each building and applying its whole directory. |
| `OCIRepository` | 10m | | How soon a `semver` range picks up a new chart. |
| `HelmRelease` | 5m | | Checks the Helm release and remediates a failed one, without building anything. It doesn't undo changes made by hand in the workload cluster unless you set `spec.driftDetection`, see [Correct changes made by hand](../how-to/update-app.md#correct-changes-made-by-hand). |

`retryInterval` retries a failed `Kustomization` after a minute instead of the next `interval`. An apps `Kustomization`
whose cluster isn't ready yet checks again every 30 seconds whatever its interval, as `dependsOn` does.

[flux-receiver]: https://fluxcd.io/flux/components/notification/receivers/

## Variables

The bases use variables where every cluster needs its own value, such as `${cluster_name}`. The workload cluster's Flux
`Kustomization` sets them in `spec.postBuild.substitute`, so one base works for every cluster:

| Variable | What it's for |
| --- | --- |
| `cluster_name` | The workload cluster's name. It names the cluster's resources and its apps, such as `${cluster_name}-hello-world`, and the `<cluster>-kubeconfig` Secret and `<cluster>-cluster-values` ConfigMap the apps read. `release-aws` rejects a name longer than 20 characters. |
| `organization` | The organisation the cluster belongs to. Its resources go into the `org-${organization}` namespace, and `bases/clusters/capa` sets it as `global.metadata.organization` in the chart values. `namespace.yaml` fills it in from the organisation's `Organization`, see [The organisation's name](#the-organisations-name). |
| `release` | The Giant Swarm release the cluster runs: the version of the `release-aws` chart in `bases/clusters/capa`. Without it, the `OCIRepository` has no chart version to pull and the cluster doesn't install. |
| `cluster_description` | A free-text description of the cluster, set as `global.metadata.description` by `bases/clusters/capa`. |

Each of a cluster's `Kustomization`s sets the variables of what it applies. Only the cluster base uses `release` and
`cluster_description`, so the cluster's own `Kustomization` sets all four, and the apps and `-direct` ones only
`cluster_name` and `organization`.

Set every variable the cluster's bases use. Flux replaces a variable that isn't set with an empty string; CI fails on
it instead, see [Jobs](./ci-checks.md#jobs). CI reads only `spec.postBuild.substitute`, not
`spec.postBuild.substituteFrom`, so a variable set only in `substituteFrom` fails CI, although Flux sets it on the
cluster.

Flux substitutes variables in what a `Kustomization` applies, never in the `Kustomization`'s own spec. Where a
cluster's `Kustomization` needs the organisation's name, it writes `${organization}`, which `namespace.yaml` fills in
when it applies the file.
